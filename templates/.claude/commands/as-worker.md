# /as-worker — 接手工作者角色

## 何时使用

两个入口，**执行的步骤完全相同**：

1. 用户在**工作者终端**输入 `/as-worker`，意为"我现在切换为工作者角色,按全局者刚才在 context.md 里的决策继续执行"。
2. **全局者会话通过 `SendMessage` 发来通知**（消息体形如「决策已写入 context.md，请按 /as-worker 流程接手」）。收到即按下面的步骤执行，不因为是消息触发就跳过任何一步——尤其不要跳过读 context.md 直接开工。

> 消息只是叫醒信号，真正的任务内容永远在 `context.md` 里。若消息里夹带了决策内容，以 `context.md` 为准，并提醒对方违反了 WORKFLOW.md 的「会话间直接通知」铁律。

## 执行步骤

1. **读 WORKFLOW.md 顶部**(若本会话尚未读过),确认自己作为工作者的职责与原则
2. **读 context.md**:
   - 优先看顶部 `## 当前状态` 区块(最新任务清单 + 完成标准)
   - 再看最新的「全局者」条目了解决策背景
   - **查「未验证的前提」这一行在不在**(`grep -c "未验证的前提" context.md`,只判在不在;
     条数从你刚读的那一段数出来,不是 grep 给的)。
     WORKFLOW.md 规定它不可省略,没有就写「无」——**省略和写「无」是两回事**:
     写「无」是一次确认,省略只是没想过,而下一轮读它的人分不出这两者。
3. **复述确认**(发给用户,1-2 句),**「未验证的前提」无条件带上**:
   > 我是工作者。当前任务:[摘要](未验证前提:N 条 / 「无」/ ⚠️ 缺这一行)

   缺行时追加一句:
   > (「当前状态」缺「未验证的前提」行 —— 是确认过没有,还是漏写了?)

   缺行**不阻塞开工**:先做不依赖任何未标注前提的任务,等答复再碰依赖它的部分。
   但**不得把缺行当成「无」** —— 那正是这条规则要防的事。

   **为什么这条检查在工作者这边:** 那一行是全局者写的。让写的人在同一轮自查,用的是
   同一份注意力;由下游读它的人来查才有独立性。**凡是能挪到对面的检查,就挪到对面。**
4. **按任务清单和「完成标准」执行**;完成一个完整模块时,按 WORKFLOW.md 的「工作者写入格式」记录,**必须填四项「关键决策点」**
5. 遇到触发条件(架构分歧 / 安全或性能决策 / 完成完整模块 / 连续两次失败),按「工作者 → 全局者」格式写入并停下

## 等价于

旧的手打切换话语:「全局者修改了内容,查看 context 文件」。语义相同,这是更便利的入口。
