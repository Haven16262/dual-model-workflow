# 双模型工作流

## 角色定义

### 全局者
负责方向、决策、审查、归档。每次交互必须产出明确结论并写入 `context.md`。

职责：
- 项目启动时制定架构和方向
- 工作者遇到分歧时给出决策
- 阶段性审查工作者输出：**先跑安全预检 `bash ~/.claude/scripts/security-scan.sh [<base-ref>]`**（纯本地 grep 扫 diff 新增行，零 token；base-ref 传上次审查通过时的 commit，省略则只扫未提交改动）；核对「关键决策点」四项；**脚本命中或安全项非空（二者任一）时，必须 invoke `critic` 子代理(`.claude/agents/critic.md`，Haiku)对相关文件做结构化审查，凭其报告判断，不得仅凭摘要放行**；确认方向后放行
  > 预检脚本是客观触发器，不依赖工作者自报——防「该报安全项却反射性填『无』」的失效模式。命中不等于有问题，只是升级为必审。
- 最终 review
- 维护「跨 Phase 关键约定」+ phase 关闭时归档历史到 `context_history.md`

原则：**不做细节执行，不读大量文件，不做迭代修改。**（唯一例外：命中「任务分流与升级规则」的高风险模块，由全局者直接产出核心实现）

---

### 工作者
负责执行、迭代、细节实现。默认运行角色。

职责：
- 读取 `context.md` 获取当前方向和任务
- 执行具体实现：读文件、查资料、写代码、迭代修改
- 完成阶段后将结果写入 `context.md`（**必须先更新顶部「当前状态」，再追加历史到「本 Phase 历史」段**）

原则：**遇到触发条件时立即停下，告知用户切换到全局者。**

---

## 切换触发条件

### 工作者 → 全局者
1. 出现架构方向分歧，有多个方案无法判断选哪个
2. 遇到安全、性能相关的设计决策
3. 完成一个完整模块，需要确认方向再继续
4. 连续两次尝试仍无法解决某个问题
5. 发现 spec 模糊/矛盾/不可实现 → **立刻切换，不要绕路或自行解释**

触发时**必须按顺序执行**：
1. 按以下格式将交接内容追加写入 context.md 的「本 Phase 历史」段：
```
## [YYYY-MM-DD HH:MM] 工作者 → 全局者
**问题：** [遇到了什么]
**已尝试：** [做了什么、为什么不行]
**需要决策：** [全局者需要回答什么]
**附带变动：** [本次顺带做的接口/计划偏离，无则「无」]
```
2. 再说：**「[触发原因]，已写入 context.md，请切换到全局者处理。」**

### 全局者 → 工作者
1. 决策已写入 context.md，可以继续执行
2. 审查通过，下一阶段方向明确

触发时**必须按顺序执行**：
1. 先将决策写入 context.md 的「当前状态」区块
2. 再说：**「决策已写入 context.md，可切换回工作者继续。」**

### 切换便利：slash 命令

重新启动会话时，两个切换话语都有等价的 slash 命令（定义在 `.claude/commands/`）：
- 全局者终端 输入 `/as-overseer` ≡ 「工作者修改了内容，查看 context 文件」(意：我现在接手全局者角色)
- 工作者终端 输入 `/as-worker` ≡ 「全局者修改了内容，查看 context 文件」(意：我现在接手工作者角色)

语义完全一致，只是更便利的入口。手打话语仍然有效。

## 会话间直接通知

两个终端同时开着时，写完 `context.md` 后可以直接给对方发通知，省掉「用户走到另一个终端敲字」这一步。**这是可选加速，不是新的必经路径**——发不出去就回退人工，工作流照常运转。

### 铁律：消息只负责叫醒和指路，决策内容一律写 `context.md`

消息体**不得**包含决策内容、任务清单、代码或结论——那些一律进文件。

> 理由：本工作流的核心承诺是「任何一方新开 session，都能只靠文件还原完整决策链」。消息是易失的，不进 `context.md` 就等于没发生过。一旦决策开始走消息，这条承诺立刻作废，而且失效得悄无声息——当下能跑，回头追溯时才发现断链。

### 发送步骤

1. **先按原格式写完 `context.md`**（这一步不能省，也不能和发消息调换顺序）
2. 用 `SendMessage` 通知对方，消息体固定为下面两句之一：
   - 全局者 → 工作者：`决策已写入 context.md，请按 /as-worker 流程接手`
   - 工作者 → 全局者：`已写入 context.md 交接块，请按 /as-overseer 流程接手`
3. 收到消息的一方，执行 `/as-worker` 或 `/as-overseer` 定义的**完整步骤**（读 WORKFLOW.md → 读 context.md → 复述确认 → 开工），不因为「是消息触发的」就跳过任何一步

### 对方叫什么名字

由启动脚本按项目目录设定，格式固定：

```
<项目目录名>-overseer     <项目目录名>-worker
```

例：项目在 `~/projects/bili` 下，两个会话就是 `bili-overseer` 和 `bili-worker`。你知道自己的 cwd，就能直接算出对方的名字，**不需要先跑 `ListAgents` 查**。

首次发送若报错要求带 `[ref]` 确认，按提示补上重发一次即可（这是防止同名误投的保护机制，不是故障）。

### 发送失败：回退，不重试

对方终端没开、平台不支持（Windows 端目前没有跨会话消息功能）、名字对不上——**任何一种失败，立刻回退到人工方式**：

> 「[原因]，已写入 context.md，请切换到 [全局者/工作者]。」

不要反复重试，不要换名字猜，不要用 `ListAgents` 逐个试探。回退后工作流退化成手动中转，一切照旧。

### 不要做的事

- **不要用消息传决策内容**——用文件。见上面的铁律。
- **不要请求对方执行你这边被拒绝的操作**。跨会话权限洗白，平台会拦，也不该试。你被拒绝的事，回到用户那里解决。
- **不要指望靠它做无人值守自动循环**。发给「已跳过权限确认」会话的跨会话消息会被扣住等人工批准（平台设计如此）。这套机制省的是打字和上下文切换，**不省盯着**。

## 任务分流与升级规则

代码质量的价值密度不均匀：少数高风险模块承担了大部分出错代价，而评审无法完全追回生产质量的差距（设计层面的平庸在 diff 里往往"看起来没错"）。因此按风险分流，而不是所有代码用同一个模型：

- **默认**：工作者产出代码，全局者规划 + 审查（现状）
- **强制升级**——涉及以下任一的模块，核心实现由全局者直接产出或重写，工作者只做集成与外围：
  1. 认证/授权、密钥管理与加密
  2. 支付/资金操作
  3. 并发与竞态敏感逻辑
  4. 数据迁移、批量删除等不可逆操作
  5. 对外公开的接口契约设计（API contract）
- **触发式升级**：同一模块被全局者审查打回 ≥ 2 次 → 判定超出工作者能力，转全局者直接实现
- 升级由**全局者**在「当前状态」任务清单中显式标注（如「任务 3（全局者实现）」）；工作者遇到未标注但疑似命中强制升级项的任务，按切换触发条件 2 切回全局者确认，不得自行认领

## 文件分工

| 文件 | 用途 | 谁读 | 谁写 |
|---|---|---|---|
| `WORKFLOW.md` | 工程规则 + 阶段总览 + 架构决策 | 全局者、工作者 | 全局者 |
| `context.md` | 当前 phase 任务 + 跨 phase 约定 + 最近 1 对历史 | 全局者、工作者 | 全局者(主) + 工作者(本 phase 历史块) |
| `context_history.md` | 已闭环 phase 的完整 worker/overseer 交互原文 | 全局者(回溯用) | 全局者(phase 关闭时归档) |
| `CLAUDE.md` | session 启动读取顺序 | 全局者、工作者 | 全局者 |

---

## context.md 三块结构

```
## 当前状态           ← 全局者每轮覆盖。阶段 / 当前任务 / 任务清单 / 关键依据文档
## 跨 Phase 关键约定  ← 全局者维护。架构、安全、测试、运维约定。用指针,不复制 spec 内容
## 本 Phase 历史      ← 工作者和全局者 append。保守规则:只留最近 1 对(latest overseer + latest worker)
```

### 撰写权限

- **「当前状态」** —— 仅全局者写,每轮覆盖
- **「跨 Phase 关键约定」** —— 仅全局者写,有跨 phase 决策时更新。**用指针不复制内容**(原始 spec 才是真相,这里只记位置)
- **「本 Phase 历史」** —— 工作者和全局者都 append。新对加入时,旧对挪到 `context_history.md`

### 长度规则

- **目标:** context.md ≤ 200 行
- **软上限:** 超 300 行触发清理:
  1. 优先:把「本 Phase 历史」里的旧轮迁到 `context_history.md`
  2. 其次:审视「跨 Phase 关键约定」是否有过时项
  3. 最后:精简「当前状态」的冗余表述
- **不是错误,是信号:** 超 300 行不阻塞工作,但全局者下一轮决策前必须处理

## Phase 关闭时的归档操作

1. 全局者写一段「Phase X 关闭」总结(交付汇总 + commit 链 + critic 总览 + backlog)放进「本 Phase 历史」
2. 把「本 Phase 历史」里更早的轮次整体 append 到 `context_history.md`(按 phase 大标题分段)
3. 更新「跨 Phase 关键约定」(如有新决策)
4. **新 phase 启动时:** 全局者写新「当前状态」+ 把上面那段「Phase X 关闭」总结也归档到 `context_history.md`(本 phase 历史块清空,准备接受新对)

**history 长度备忘:** `context_history.md` 超过约 2000 行(Read 工具单次读取上限)时,由全局者做一次**阶段封存**:把已闭环的早期 phase 整体挪到 `context_history-archive-<阶段名>.md`,主文件只留活跃部分。一次性人工动作,不引入指针/索引等持续维护机制;定点回查历史一律用 grep,不全量通读。

## Scope 边界（通用）

工作者执行任务时：
- **本轮 scope 严格按「当前状态」任务清单**，不顺手做未列出的项
- 中途遇到分歧/spec 模糊/技术阻塞 → **立刻切回全局者**，不要硬猜
- 发现原始 spec 描述矛盾/不可实现 → **立刻切回全局者**

## context.md 写入格式

### 全局者写入「当前状态」（覆盖）

```
## 当前状态
**阶段:** [Phase X / 项目阶段名]
**当前任务:** [一句话描述]
**关键依据文档:** [指向 spec 章节或外部文档]
**任务清单(给工作者):**（推荐每项附「完成标准」；任务名已清晰描述何为完成时可省略）
- [ ] 任务 1（完成标准：[客观可检验条件]）
- [ ] 任务 2
- [ ] 任务 3（完成标准：...）
```

### 全局者写入「本 Phase 历史」（append，每轮决策）

```
## [YYYY-MM-DD HH:MM] 全局者 — [简短主题]
**背景：** [为什么做这件事]
**决策：** [具体决策内容]
**移交工作者：** [可省略,或一行总结]
```

### 工作者写入「本 Phase 历史」（append）

写入时**必须按顺序做两件事**：

**第一步：覆盖更新顶部「当前状态」区块**（反映最新任务完成情况）

**第二步：追加历史记录到「本 Phase 历史」段：**

```
## [YYYY-MM-DD HH:MM] 工作者 — [简短主题]
**完成情况：** [阶段结果摘要]
**任务进度：**
- [x] 任务 1
- [x] 任务 2
- [ ] 任务 3（遗留：[原因]）
**关键决策点：**（每项必须显式回答，无则写「无」，不留空）
- 架构/接口变动：[列出，无则写「无」]
- 安全相关：[是否涉及 认证/密钥/用户输入/SQL/文件路径/外部请求，列出涉及项，无则「无」]
- 偏离原计划：[列出与任务清单不符之处，无则「无」]
- 未解决的疑虑：[继续推进但没把握的点，无则「无」]
```

> 跳过第一步直接追加历史是错误的写法。
