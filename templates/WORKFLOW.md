# 双模型工作流

## 角色定义

### 全局者
负责方向、决策、审查、归档。每次交互必须产出明确结论并写入 `context.md`。

职责：
- 项目启动时制定架构和方向
- 工作者遇到分歧时给出决策
- 阶段性审查工作者输出：**先跑安全预检 `bash ~/.claude/scripts/security-scan.sh [<base-ref>]`**（纯本地 grep 扫 diff 新增行，零 token；base-ref 传上次审查通过时的 commit，省略则只扫未提交改动）；核对「关键决策点」四项；**脚本命中或安全项非空（二者任一）时，必须 invoke `critic` 子代理(`.claude/agents/critic.md`，Haiku)对相关文件做结构化审查，凭其报告判断，不得仅凭摘要放行**；确认方向后放行
  > 预检脚本是客观触发器，不依赖工作者自报——防「该报安全项却反射性填『无』」的失效模式。命中不等于有问题，只是升级为必审。
- 最终 review
- 维护「跨 Phase 关键约定」+ phase 关闭时归档历史到 `context_history.md`

原则：**不做细节执行，不读大量文件，不做迭代修改。**（唯一例外：命中「任务分流与升级规则」的高风险模块，由全局者直接产出核心实现）

> **critic 子代理的可用前提（务必知道）：** 项目级 `critic` 只在「从项目目录启动 cc」时才被注册（`cd <项目目录> && cc`）——cc 在启动那一刻按项目根扫描 `.claude/agents/`，事后 Bash `cd` 不会重扫、也不改项目根。若 session 在别处（如 `/root`）启动、不便重启 → **退用内置 `security-reviewer` 当等价 critic**：在 prompt 里约束它**只读（不 Edit/Write）、只查全局者指定的安全维度、按 critic 报告格式输出**；关键结论仍由全局者独立复算二次确认，不凭子代理单方放行。一劳永逸做法：把 `critic.md` 拷一份到用户级 `~/.claude/agents/`，则任何启动目录都可用。

---

### 工作者
负责执行、迭代、细节实现。默认运行角色。

职责：
- 读取 `context.md` 获取当前方向和任务
- 执行具体实现：读文件、查资料、写代码、迭代修改
- 完成阶段后将结果写入 `context.md`（**必须先更新顶部「当前状态」，再追加历史到「本 Phase 历史」段**）

原则：**遇到触发条件时立即停下，告知用户切换到全局者。**

## 切换触发条件

### 工作者 → 全局者
1. 出现架构方向分歧，有多个方案无法判断选哪个
2. 遇到安全、性能相关的设计决策
3. 完成一个完整模块，需要确认方向再继续
4. 连续两次尝试仍无法解决某个问题
5. 发现 spec 模糊/矛盾/不可实现 → **立刻切换，不要绕路或自行解释**

触发时**必须按顺序执行**：
1. 按以下格式将交接内容追加写入 context.md 的「本 Phase 历史」段：
```
## [YYYY-MM-DD HH:MM] 工作者 → 全局者
**问题：** [遇到了什么]
**已尝试：** [做了什么、为什么不行]
**需要决策：** [全局者需要回答什么]
**附带变动：** [本次顺带做的接口/计划偏离，无则「无」]
```
2. 再说：**「[触发原因]，已写入 context.md，请切换到全局者处理。」**

### 全局者 → 工作者
1. 决策已写入 context.md，可以继续执行
2. 审查通过，下一阶段方向明确

触发时**必须按顺序执行**：
1. 先将决策写入 context.md 的「当前状态」区块
2. 再说：**「决策已写入 context.md，可切换回工作者继续。」**

### 切换便利：slash 命令

重新启动会话时，两个切换话语都有等价的 slash 命令（定义在 `.claude/commands/`）：
- 全局者终端 输入 `/as-overseer` ≡ 「工作者修改了内容，查看 context 文件」(意：我现在接手全局者角色)
- 工作者终端 输入 `/as-worker` ≡ 「全局者修改了内容，查看 context 文件」(意：我现在接手工作者角色)

语义完全一致，只是更便利的入口。手打话语仍然有效。

## 会话间直接通知

两个终端同时开着时，写完 `context.md` 后可以直接给对方发通知，省掉「用户走到另一个终端敲字」这一步。**这是可选加速，不是新的必经路径**——发不出去就回退人工，工作流照常运转。

> 版本要求：macOS / Linux / WSL 2 需 Claude Code ≥ 2.1.224，原生 Windows ≥ 2.1.234。
>
> **本节只管同一台机器上的两个终端。** 跨机器是另一套规则：对方按它的 Remote Control 名字寻址（回复时直接抄收到消息的 `from`，不要用本节的四段式名字去拼），决策内容走两端共享的 git 仓库——**先 push，再发指针消息**。完整规则见 dual-model-workflow 仓库的 `CROSS-MACHINE.md`。

### 铁律：消息只负责叫醒和指路，决策内容一律写 `context.md`

消息体**不得**包含决策内容、任务清单、代码或结论——那些一律进文件。

> 理由：本工作流的核心承诺是「任何一方新开 session，都能只靠文件还原完整决策链」。消息是易失的，不进 `context.md` 就等于没发生过。一旦决策开始走消息，这条承诺立刻作废，而且失效得悄无声息——当下能跑，回头追溯时才发现断链。

### 发送步骤

1. **先按原格式写完 `context.md`**（这一步不能省，也不能和发消息调换顺序）
2. 用 `SendMessage` 通知对方，消息体固定为下面两句之一：
   - 全局者 → 工作者：`决策已写入 context.md，请按 /as-worker 流程接手`
   - 工作者 → 全局者：`已写入 context.md 交接块，请按 /as-overseer 流程接手`
3. 收到消息的一方，执行 `/as-worker` 或 `/as-overseer` 定义的**完整步骤**（读 WORKFLOW.md → 读 context.md → 复述确认 → 开工），不因为「是消息触发的」就跳过任何一步

### 对方叫什么名字

由启动脚本设定，格式是**四段**：

```
<机器标识>-<项目目录名>-<角色>-<本轮话题>
```

例：项目在 `~/projects/bili` 下，VPS 上的两个会话叫 `vps-bili-overseer-登录态重构` 和 `vps-bili-worker-0820-1145`（启动时没填话题就退化成时间戳）。

机器标识取自各机器的 `~/.claude/machine-tag`（`vps` / `msi` / …），**不是**为了让 AI 分辨机器——跨机器时对方显示的是 Remote Control 名字，那个本来就带主机名。它是给**人**用的：同一个 git 仓库在两台机器上目录名相同 → slug 相同 → 不加前缀的话，claude.ai 和手机的会话列表里会出现两条逐字相同的条目，你点进去才知道是哪台。该文件不存在时不加前缀，前三段格式不变。

**前三段你算得出，最后一段你算不出**——话题是对方在它自己的终端启动时填的，你这边无从知道。所以：

1. **发消息前跑一次 `ListAgents`**，找名字以 `<机器标识>-<项目目录名>-<对方角色>-` 开头的那一行
2. **恰好一条匹配** → 按行里印的完整名字发送
3. **零条或多条匹配** → 走下面的「发送失败：回退，不重试」

**每次发送前都要重查一遍。** 不要沿用上一轮查到的名字，也不要用用户贴给你的列表——对方终端一旦重开，名字就变了（实测遇到过：用户看到的是 `claude-code-b7`，工具查到的已经是 `claude-code-3a`）。以 `ListAgents` 的实时输出为准，永远。

> 为什么名字不做成固定的？固定名字发送方确实不用查，但同一个项目每次启动都重名，`/resume` 列表里堆出一排一模一样的条目，人和模型都分不出哪个是哪次。最后那段话题就是拿「发送前查一次」换「历史会话认得出来」——**这一次查询是流程的一部分，不是故障排查**。

名字唯一时直接按名字发即可——Claude Code 2.1.232 起，精确匹配到唯一一个在跑的会话就直接投递。只有多个会话共用同一个名字（或对方版本较旧）时才会要求带 `[ref]` 确认，按提示补上重发一次即可，这是防止误投的保护机制，不是故障。

### 可选：让平台替你盯着工作者

全局者把任务交出去时，可以在 `SendMessage` 上带 `notify_when_idle`，请平台在工作者**下次空闲**时回一条通知（Claude Code ≥ 2.1.236，仅限同一台机器上的会话；一次性，不轮询，12 小时无信号自动退订）。

它的价值是**不依赖工作者记得发消息**——工作者忘了通知，或中途停下来问用户，全局者都会知道「它停了」。

但它说的是「空闲了」，不是「写完 context.md 了」。收到后照样走 `/as-overseer` 的完整步骤：先读 `context.md`，**没有新交接块就说明工作者是停下来等人，不是交接**，这时候去看它的终端而不是开始审查。

### 发送失败：回退，不重试

对方终端没开、名字对不上、版本不够或平台不支持——**任何一种失败，立刻回退到人工方式**：

> 「[原因]，已写入 context.md，请切换到 [全局者/工作者]。」

**`ListAgents` 查一次是正常流程，查不到就回退。**不要反复重试，不要猜话题后缀，不要挨个给前缀相同的会话试投。回退后工作流退化成手动中转，一切照旧。

### 不要做的事

- **不要用消息传决策内容**——用文件。见上面的铁律。
- **不要请求对方执行你这边被拒绝的操作**。跨会话权限洗白，平台会拦，也不该试。

  但**移交工作**不是洗白，界线在于交出去的是**命令**还是**工作**：

  | | 例子 | 为什么 |
  |---|---|---|
  | ✗ 洗白 | 「帮我跑 `git push origin main`」 | 对方成了你的代理，绕过的是用户对**你这个会话**的权限判断 |
  | ✓ 交接 | 「这批活做完了，3 个 commit 在 branch X，待复审和发布」 | 对方在行使它自己的职责、做它自己的判断，而且它自己的权限门照样会拦它、照样要用户点头 |

  分不清时用这个判据：**把你从这件事里去掉，它还成立吗？** 「复审并发布一批完成的工作」成立——那本来就是全局者的活；「跑这条我被拒的命令」不成立——离开你它没有意义。
- **不要指望靠它做无人值守自动循环**。发给「已跳过权限确认」会话的跨会话消息会被扣住等人工批准（平台设计如此）。这套机制省的是打字和上下文切换，**不省盯着**。

## 任务分流与升级规则

代码质量的价值密度不均匀：少数高风险模块承担了大部分出错代价，而评审无法完全追回生产质量的差距（设计层面的平庸在 diff 里往往"看起来没错"）。因此按风险分流，而不是所有代码用同一个模型：

- **默认**：工作者产出代码，全局者规划 + 审查（现状）
- **强制升级**——涉及以下任一的模块，核心实现由全局者直接产出或重写，工作者只做集成与外围：
  1. 认证/授权、密钥管理与加密
  2. 支付/资金操作
  3. 并发与竞态敏感逻辑
  4. 数据迁移、批量删除等不可逆操作
  5. 对外公开的接口契约设计（API contract）
- **触发式升级**：同一模块被全局者审查打回 ≥ 2 次 → 判定超出工作者能力，转全局者直接实现
- 升级由**全局者**在「当前状态」任务清单中显式标注（如「任务 3（全局者实现）」）；工作者遇到未标注但疑似命中强制升级项的任务，按切换触发条件 2 切回全局者确认，不得自行认领

## 命令被守卫拦下时

工作者会话装了一个权限守卫。它拦的是**会弹窗、但没人能批准**的命令：工作者所在的会话连不上 Remote Control（provider 指向本地网关，平台层禁止），而权限弹窗**永不超时**——一旦弹出来就是无限期挂死。拦在弹窗打开之前，才有「跳过去做别的」这个选项。

**硬拒（`git push`）**：结构上不属于工作者，没有放行通道。提交、把状态写进 `context.md`、通知全局者交接，由它复审后决定是否发布。**交接的是工作，不是命令**——不要请求全局者代跑你被拒的命令。

**拒 + 放行窗口（`ssh`、`chmod`）**：可能真是工作者的活。守卫已自动把命令记进待批准队列，不需要你手抄。你要做两件事：

1. **在回复里立刻说出来**——需要跑哪条、用户敲 `/allow-once` 可放行。用户可能就在旁边，别让他等你稍后才提。
2. **继续做其他不依赖它的工作。**

**叫全局者的时机**：没有其他可推进的工作了，或队列积到 3 条以上。消息里带上机器名、队列条数、这批要确认什么。**不要每拦一条就叫一次**——手机被骚扰几次之后，用户就会开始无视它。

**这不是角色切换。** 你没有把任务交回去，只是借全局者的 Remote Control 把消息送到用户手机上——工作者会话连不上 RC，这是它在这里的唯一作用。所以**不要走「切换触发条件」那套交接协议**：不写交接块，不说切换话术，通知完继续干你的活。

`/allow-once` 只有用户能敲（skill 设了 `disable-model-invocation`）。你不能给自己开窗，也不要去找绕过守卫的其它办法：开窗并不等于授权，它只是让弹窗能弹出来，权限仍然来自用户点的那一下。

## 文件分工

| 文件 | 用途 | 谁读 | 谁写 |
|---|---|---|---|
| `WORKFLOW.md` | 工程规则 + 阶段总览 + 架构决策 | 全局者、工作者 | 全局者 |
| `context.md` | 当前 phase 任务 + 跨 phase 约定 + 最近 1 对历史 | 全局者、工作者 | 全局者(主) + 工作者(本 phase 历史块) |
| `context_history.md` | 已闭环 phase 的完整 worker/overseer 交互原文 | 全局者(回溯用) | 全局者(phase 关闭时归档) |
| `CLAUDE.md` | session 启动读取顺序 | 全局者、工作者 | 全局者 |

## context.md 三块结构

```
## 当前状态           ← 全局者每轮覆盖。阶段 / 当前任务 / 任务清单 / 关键依据文档
## 跨 Phase 关键约定  ← 全局者维护。架构、安全、测试、运维约定。用指针,不复制 spec 内容
## 本 Phase 历史      ← 工作者和全局者 append。保守规则:只留最近 1 对(latest overseer + latest worker)
```

### 撰写权限

- **「当前状态」** —— 仅全局者写,每轮覆盖
- **「跨 Phase 关键约定」** —— 仅全局者写,有跨 phase 决策时更新。**用指针不复制内容**(原始 spec 才是真相,这里只记位置)
- **「本 Phase 历史」** —— 工作者和全局者都 append。新对加入时,旧对挪到 `context_history.md`

### 写作契约（三条）

`context.md` 的主要读者是模型，不是人。这不意味着要写成电报体——**没有「AI 文风」这回事**，缩写和去虚词只会丢信息。真正的差别只有三条，而且都不是风格问题：

**1. 自足。** 判据：**「当前状态」区块，能不能被一个刚启动、什么都没读过的模型直接执行？** 人的交接可以写「继续昨天那个」，因为人有连续记忆；模型没有，而且每一轮都是新的。不能自足就是没写够。

**2. 标注验证状态。** 模型会自信地基于一条声明行动，不会先问「这条核实过吗」。所以已验证的和推测/待验证的**分开写**，不要混在同一段里。混写的后果不是少一条信息，是让一条未经核实的判断在下一轮以事实的身份被使用。

**3. 绝对化。** 路径写全、日期写绝对值、文件名写全称。不要「上面那个方案」「第三封」「昨天」「刚才改的那个」——人能从上下文还原，模型会**错认且不自知**。

反过来，有一样东西**不要**为了省 token 删掉：**理由**。没有 why 的规则，模型会把它当成可优化的对象然后「改进」掉；人会犹豫一下，模型不会。所以关键约定要连着当初为什么这么定一起写。

### 长度规则

- **目标:** context.md ≤ 200 行
- **软上限:** 超 300 行触发清理:
  1. 优先:把「本 Phase 历史」里的旧轮迁到 `context_history.md`
  2. 其次:审视「跨 Phase 关键约定」是否有过时项
  3. 最后:精简「当前状态」的冗余表述
- **不是错误,是信号:** 超 300 行不阻塞工作,但全局者下一轮决策前必须处理
- **谁来触发:** 同 history —— `/as-overseer` 第 2-3 步每轮无条件打印 `context.md` 行数,≥300 时附一句清理提示。这两条长度规则是一对,别只给其中一条装触发器。

## Phase 关闭时的归档操作

1. 全局者写一段「Phase X 关闭」总结(交付汇总 + commit 链 + critic 总览 + backlog)放进「本 Phase 历史」
2. 把「本 Phase 历史」里更早的轮次整体 append 到 `context_history.md`(按 phase 大标题分段)
3. 更新「跨 Phase 关键约定」(如有新决策)
4. **新 phase 启动时:** 全局者写新「当前状态」+ 把上面那段「Phase X 关闭」总结也归档到 `context_history.md`(本 phase 历史块清空,准备接受新对)

**history 长度备忘:** `context_history.md` 超过约 2000 行(Read 工具单次读取上限)时,由全局者做一次**阶段封存**:把已闭环的早期 phase 整体挪到 `context_history-archive-<阶段名>.md`,主文件只留活跃部分。一次性人工动作,不引入指针/索引等持续维护机制;定点回查历史一律用 grep,不全量通读。

**阈值是弹性的。** 2000 只是 Read 工具单次读取上限的参考值,而定点回查本来就走 grep、真要读也可以带 offset 分段读 —— 超线不会真的读不了。所以它和「context.md 超 300 行」一样,**不是错误,是信号**,不阻塞任何工作。

**谁来触发:** 不靠记忆。`/as-overseer` 第 2-3 步每轮**无条件**打印 `context_history.md` 的行数,≥1800 行时附一句封存提示 —— 全局者每次接手都会看见。1800 而不是 2000,是为了留出封存的余量。

> 这条规则曾经真的漏过(2026-09-05 查:qq-bot 2407 行、music-player 2167 行 —— 两个项目
> 都已有 archive 文件,即会封存,但做着做着停了)。根因不是纪律:**这一段不在全局者每轮
> 的读取路径上** —— 第 1 步只读「WORKFLOW.md 顶部」。所以修法是把检查搬进每轮必经的
> 步骤,而不是把规则写得更严。

## Scope 边界（通用）

工作者执行任务时：
- **本轮 scope 严格按「当前状态」任务清单**，不顺手做未列出的项
- 中途遇到分歧/spec 模糊/技术阻塞 → **立刻切回全局者**，不要硬猜
- 发现原始 spec 描述矛盾/不可实现 → **立刻切回全局者**

## context.md 写入格式

### 全局者写入「当前状态」（覆盖）

```
## 当前状态
**阶段:** [Phase X / 项目阶段名]
**当前任务:** [一句话描述]
**关键依据文档:** [指向 spec 章节或外部文档，写全路径]
**任务清单(给工作者):**（推荐每项附「完成标准」；任务名已清晰描述何为完成时可省略）
- [ ] 任务 1（完成标准：[客观可检验条件]）
- [ ] 任务 2
- [ ] 任务 3（完成标准：...）
**未验证的前提:**（没有就写「无」，不要省略这一行）
- [某条判断] —— 依据 [来源]，本侧未复核
```

最后一行不是可选的。省略它和写「无」是两回事：写「无」是一次确认，省略只是没想过——而下一轮读它的模型分不出这两者。

### 全局者写入「本 Phase 历史」（append，每轮决策）

```
## [YYYY-MM-DD HH:MM] 全局者 — [简短主题]
**背景：** [为什么做这件事]
**决策：** [具体决策内容]
**移交工作者：** [可省略,或一行总结]
```

### 工作者写入「本 Phase 历史」（append）

写入时**必须按顺序做两件事**：

**第一步：覆盖更新顶部「当前状态」区块**（反映最新任务完成情况）

**第二步：追加历史记录到「本 Phase 历史」段：**

```
## [YYYY-MM-DD HH:MM] 工作者 — [简短主题]
**完成情况：** [阶段结果摘要]
**任务进度：**
- [x] 任务 1
- [x] 任务 2
- [ ] 任务 3（遗留：[原因]）
**关键决策点：**（每项必须显式回答，无则写「无」，不留空）
- 架构/接口变动：[列出，无则写「无」]
- 安全相关：[是否涉及 认证/密钥/用户输入/SQL/文件路径/外部请求，列出涉及项，无则「无」]
- 偏离原计划：[列出与任务清单不符之处，无则「无」]
- 未解决的疑虑：[继续推进但没把握的点，无则「无」]
```

> 跳过第一步直接追加历史是错误的写法。
