## 角色定义

### 全局者
> 全局者的职责正文在 `.workflow/overseer.md`「全局者」。工作者平时不读；被点名时读这一章。

---

### 工作者
负责执行、迭代、细节实现。默认运行角色。

职责：
- 读取 `context.md` 获取当前方向和任务
- 执行具体实现：读文件、查资料、写代码、迭代修改
- 完成阶段后先提交本轮改动（只提交，不 push），再将结果写入 `context.md`：完成情况写进自己在「本 Phase 历史」里的交接块，开头写本轮提交的 sha；**不覆盖「当前状态」的轮换部分**（那是全局者的决策），只许往 `backlog`、`未验证的前提` 末尾追加新条目（见「撰写权限」与「工作者写入「本 Phase 历史」」）

原则：**遇到触发条件时立即停下，告知用户切换到全局者。**

## 切换触发条件

### 工作者 → 全局者
1. 出现架构方向分歧，有多个方案无法判断选哪个
2. 遇到安全、性能相关的设计决策
3. 完成一个完整模块，需要确认方向再继续
4. 连续两次尝试仍无法解决某个问题
5. 发现 spec 模糊/矛盾/不可实现 → **立刻切换，不要绕路或自行解释**
   > **唯一可以不切回、自己改的是笔误类**，两条都中才算：① 事实能对照一个写得出全路径的真值来源核对
   > （如 spec 写的文件名、函数名、数值与仓库里实际的不一致，而仓库那份是对的）；② 意图无歧义，改法只有一种。
   > 改了必须写进交接块的「spec 修正」（改前 / 改后 / 依据），全局者下一轮逐条确认。
   > **设计类仍是本条，先切回**：挪零件位置、改接口、改顺序、删减范围 —— 凡是要在两种做法里选一种的都算。
   > 分不清是笔误还是设计时，按设计处理。
6. 发现「当前状态」里某条前提不成立 → 同第 5 条，**立刻切换**。前提塌了还继续推进，
   产出会建立在错的地基上；改不改方向是全局者的判断，不是你自行调整的范围
   > **不要套用第 4 条。** 第 4 条要求「连续两次尝试」才切换 —— 前提已经塌了还先试两次，
   > 正是第 5 条禁止的「绕路或自行解释」。前提证伪是立刻切换，不用先尝试。
   > **标记不由你改**：工作者不改已有条目（见「撰写权限」），所以在交接块「问题」里写明是哪条前提、怎么证伪的、证据在哪；
   > 由全局者接手后把「当前状态」里原来那条「- [ ]」改成「⚠️ 已证伪」条目（格式见「全局者写入「当前状态」」），并列出受影响的决策。

触发时**必须按顺序执行**：
1. 将交接块追加写入 context.md 的「本 Phase 历史」段（时间戳先跑 `date '+%Y-%m-%d %H:%M'` 取，见「context.md 写入格式」）。
   **第 3 条（完成一个完整模块）用「工作者写入「本 Phase 历史」」一节的完成阶段格式**（含闸门结果、spec 修正、关键决策点），不另写下面这块；
   其余各条用下面的格式：
```
## [YYYY-MM-DD HH:MM] 工作者 → 全局者
**问题：** [遇到了什么]
**已尝试：** [做了什么、为什么不行]
**需要决策：** [全局者需要回答什么]
**附带变动：** [本次顺带做的接口/计划偏离，无则「无」]
**spec 修正：** [本轮改过的笔误类，写法同完成阶段格式；无则「无」]
```
   写完（完成阶段格式的块也一样）先跑 `python3 ~/.claude/scripts/handoff-check.py --fresh 120`：只读，机械核对交接块的标签、提交行、闸门 `rc=`、「当前状态」两行、时间戳、有无行首 `workflow-mode:`；退出 0 才往下，退出 3 按它列的补齐、重跑；脚本不存在时在块末补一行 `**handoff-check：** 脚本不存在`，不阻塞。
2. 在项目根目录跑 `python3 ~/.claude/scripts/sessions-md.py . --note "<本会话到目前为止做了什么，一句话>"`，把本会话登记进 `sessions.md`（见「文件分工」）。`--note` 每次覆盖自己那一行，写累计的一句，不写本轮流水。退出码非 0 不阻塞交接：在刚写的交接块末尾补一行 `**sessions.md：** rc=<退出码>，<报错首行>`，再做下一步。
3. 再说：**「[触发原因]，已写入 context.md，请切换到全局者处理。」**

### 全局者 → 工作者
> 全局者交接给工作者的步骤在 `.workflow/overseer.md`「全局者 → 工作者」。工作者平时不读；被点名时读这一章。

> 两个方向的第 2 步每次交接都跑，不是只在会话结束时跑：最后一次交接写进去的就是终稿，不用判断哪次是最后一次；崩溃、被 kill 的会话，机械列由下一次任何角色跑脚本时补上。不经交接就要结束会话（例如被要求关闭）时，写完 context.md 后同样跑一次。

### 切换便利：slash 命令

重新启动会话时，两个切换话语都有等价的 slash 命令（定义在 `.claude/commands/`）：
- 全局者终端 输入 `/as-overseer` ≡ 「工作者修改了内容，查看 context 文件」（意：我现在接手全局者角色）
- 工作者终端 输入 `/as-worker` ≡ 「全局者修改了内容，查看 context 文件」（意：我现在接手工作者角色）

语义完全一致，只是更便利的入口。手打话语仍然有效。

## 会话间直接通知

两个终端同时开着时，写完 `context.md` 后可以直接给对方发通知，省掉「用户走到另一个终端敲字」这一步。**这是可选加速，不是新的必经路径**——发不出去就回退人工，工作流照常运转。

> 版本要求：macOS / Linux / WSL 2 需 Claude Code ≥ 2.1.224，原生 Windows ≥ 2.1.234。
>
> **本节只管同一台机器上的两个终端。** 跨机器是另一套规则：对方按它的 Remote Control 名字寻址（回复时直接抄收到消息的 `from`，不要用本节的四段式名字去拼），决策内容走两端共享的 git 仓库——先 push，再发指针消息。完整规则见 dual-model-workflow 仓库的 `CROSS-MACHINE.md`。

### 铁律：消息只负责叫醒和指路，决策内容一律写 `context.md`

消息体**不得**包含决策内容、任务清单、代码或结论——那些一律进文件。

> 理由：本工作流的核心承诺是「任何一方新开 session，都能只靠文件还原完整决策链」。消息是易失的，不进 `context.md` 就等于没发生过。一旦决策开始走消息，这条承诺立刻作废，而且失效得悄无声息——当下能跑，回头追溯时才发现断链。

### 发送步骤

1. **先按原格式写完 `context.md`**（这一步不能省，也不能和发消息调换顺序）
2. 用 `SendMessage` 通知对方，消息体固定为下面两句之一：
   - 全局者 → 工作者：`决策已写入 context.md，请按 /as-worker 流程接手`
   - 工作者 → 全局者：`已写入 context.md 交接块，请按 /as-overseer 流程接手`
3. 收到消息的一方，执行 `/as-worker` 或 `/as-overseer` 定义的**完整步骤**（读 WORKFLOW.md → 读 context.md → 复述确认 → 开工），不因为「是消息触发的」就跳过任何一步

### 对方叫什么名字

由启动脚本设定，格式是**四段**：

```
<机器标识>-<项目目录名>-<角色>-<本轮话题>
```

例：项目在 `~/projects/bili` 下，VPS 上的两个会话叫 `vps-bili-overseer-登录态重构` 和 `vps-bili-worker-0820-1145`（启动时没填话题就退化成时间戳）。

机器标识取自各机器的 `~/.claude/machine-tag`（`vps` / `msi` / …），**不是**为了让 AI 分辨机器——跨机器时对方显示的是 Remote Control 名字，那个本来就带主机名。它是给人用的：同一个 git 仓库在两台机器上目录名相同 → slug 相同 → 不加前缀的话，claude.ai 和手机的会话列表里会出现两条逐字相同的条目，你点进去才知道是哪台。该文件不存在时不加前缀，前三段格式不变。

**前三段你算得出，最后一段你算不出**——话题是对方在它自己的终端启动时填的，你这边无从知道。所以：

1. **发消息前跑一次 `ListAgents`**，找名字以 `<机器标识>-<项目目录名>-<对方角色>-` 开头的那一行
2. **恰好一条匹配** → 按行里印的完整名字发送
3. **零条或多条匹配** → 走下面的「发送失败：回退，不重试」

**每次发送前都要重查一遍。** 不要沿用上一轮查到的名字，也不要用用户贴给你的列表——对方终端一旦重开，名字就变了（实测遇到过：用户看到的是 `claude-code-b7`，工具查到的已经是 `claude-code-3a`）。以 `ListAgents` 的实时输出为准，永远。

> 为什么名字不做成固定的？固定名字发送方确实不用查，但同一个项目每次启动都重名，`/resume` 列表里堆出一排一模一样的条目，人和模型都分不出哪个是哪次。最后那段话题就是拿「发送前查一次」换「历史会话认得出来」——**这一次查询是流程的一部分，不是故障排查**。

名字唯一时直接按名字发即可——Claude Code 2.1.232 起，精确匹配到唯一一个在跑的会话就直接投递。只有多个会话共用同一个名字（或对方版本较旧）时才会要求带 `[ref]` 确认，按提示补上重发一次即可，这是防止误投的保护机制，不是故障。

### 可选：让平台替你盯着工作者
> 正文在 `.workflow/overseer.md`（全局者发消息时用的选项）。工作者平时不读；被点名时读这一章。

### 发送失败：回退，不重试

对方终端没开、名字对不上、版本不够或平台不支持——**任何一种失败，立刻回退到人工方式**：

> 「[原因]，已写入 context.md，请切换到 [全局者/工作者]。」

**`ListAgents` 查一次是正常流程，查不到就回退。**不要反复重试，不要猜话题后缀，不要挨个给前缀相同的会话试投。回退后工作流退化成手动中转，一切照旧。

### 不要做的事

- **不要用消息传决策内容**——用文件。见上面的铁律。
- **不要请求对方执行你这边被拒绝的操作**。跨会话权限洗白，平台会拦，也不该试。

  但移交工作不是洗白，界线在于交出去的是命令还是工作：

  | | 例子 | 为什么 |
  |---|---|---|
  | 洗白 | 「帮我跑 `git push origin main`」 | 对方成了你的代理，绕过的是用户对你这个会话的权限判断 |
  | 交接 | 「这批活做完了，3 个 commit 在 branch X，待复审和发布」 | 对方在行使它自己的职责、做它自己的判断，而且它自己的权限门照样会拦它、照样要用户点头 |

  分不清时用这个判据：**把你从这件事里去掉，它还成立吗？** 「复审并发布一批完成的工作」成立，因为那本来就是全局者的活；「跑这条我被拒的命令」不成立，因为离开你它没有意义。
- **不要指望靠它做无人值守自动循环**。发给「已跳过权限确认」会话的跨会话消息会被扣住等人工批准（平台设计如此）。这套机制省的是打字和上下文切换，不省盯着。

## 任务分流与升级规则

代码质量的价值密度不均匀：少数高风险模块承担了大部分出错代价，而评审无法完全追回生产质量的差距（设计层面的平庸在 diff 里往往"看起来没错"）。因此按风险分流，而不是所有代码用同一个模型：

- **默认**：工作者产出代码，全局者规划 + 审查（现状）
- **强制升级**——涉及以下任一的模块，核心实现由全局者直接产出或重写，工作者只做集成与外围：
  1. 认证/授权、密钥管理与加密
  2. 支付/资金操作
  3. 并发与竞态敏感逻辑
  4. 数据迁移、批量删除等不可逆操作
  5. 对外公开的接口契约设计（API contract）
- **触发式升级**：同一模块被全局者审查打回 ≥ 2 次 → 判定超出工作者能力，转全局者直接实现
- 升级由**全局者**在「当前状态」任务清单中显式标注（如「任务 3（全局者实现）」）；工作者遇到未标注但疑似命中强制升级项的任务，按切换触发条件 2 切回全局者确认，不得自行认领

## 工作模式与旋钮表
> 正文（模式、旋钮表 K1–K10、开局外部基准、K10 第三者）在 `.workflow/overseer.md`「工作模式与旋钮表」，由全局者读。工作者平时不读；任务行或 `context.md`「工作模式」小节点名其中某一项时，读那一项。

### 模式写在哪
- 写在 `context.md`「当前状态」的常驻小节「工作模式」里，**单独一行、行首顶格**：`workflow-mode: <project|competition|research>`。
- **整个 `context.md` 里，只许这一行以 `workflow-mode:` 开头。** 别处提到模式，一律写成「模式：competition」。启动器读这一行时：没有这一行，就警告，并提示全局者先提模式；值不认识、有多行、或者有像模式行但写法不对的行，都拒绝启动。规则在 `scripts/dual-model-mode.sh`，两份启动器都调用它。
- 这三个枚举值与本表的列名、`dual-model-mode.sh` 里的匹配串逐字一致。改一处，其余几处一起改。
> 下面这一条留在本文件，因为工作者也要写这两个文件：

- **数据文件**（由会话写入，值班只读）：`.workflow/scores.tsv` 表头 `date<TAB>pkg<TAB>score`，按上传顺序，每个读出官方分的包一行；`.workflow/leaderboard.tsv` 表头 `rank<TAB>team<TAB>score<TAB>submissions<TAB>best_date`，K6 每次抓榜后整表覆盖。写错了（列名不对、非数字）值班会报错退出，并在日志里写明原因。
> （K10 第三者的部署、k10-watch 定时任务（cron / crontab）的加与摘、输入隔离的实际强度在 `.workflow/overseer.md`「K10 第三者（续）」。**工作者不得自行改 crontab（不得 `crontab -e` / 覆写）：cron 行由用户加，结项摘除要用户当面确认。** 任务行涉及 k10-watch、cron、crontab 时，先读那一块。）

## 命令被守卫拦下时

> 本节只在你安装了权限守卫时适用（见 README「工作者权限守卫」——英文 `README.md` 里叫「The Worker permission guard」，中文在 `README.zh-CN.md`；默认不装）。没装守卫就忽略本节；工作者仍然不该自行 `git push`，但此时没有任何东西替它拦着。

工作者会话装了一个权限守卫。它拦的是**会弹窗、但没人能批准**的命令：工作者所在的会话连不上 Remote Control（provider 指向本地网关，平台层禁止），而权限弹窗永不超时——一旦弹出来就是无限期挂死。拦在弹窗打开之前，才有「跳过去做别的」这个选项。

**硬拒（`git push`）**：结构上不属于工作者，没有放行通道。提交、把状态写进 `context.md`、通知全局者交接，由它复审后决定是否发布。**交接的是工作，不是命令**——不要请求全局者代跑你被拒的命令。

**拒 + 放行窗口（`ssh`、`chmod`）**：可能真是工作者的活。守卫已自动把命令记进待批准队列，不需要你手抄。你要做两件事：

1. **在回复里立刻说出来**——需要跑哪条、用户敲 `/allow-once` 可放行。用户可能就在旁边，不要拖到稍后才提。
2. **继续做其他不依赖它的工作。**

**叫全局者的时机**：没有其他可推进的工作了，或队列积到 3 条以上。消息里带上机器名、队列条数、这批要确认什么。**不要每拦一条就叫一次**——手机被骚扰几次之后，用户就会开始无视它。

这不是角色切换。你没有把任务交回去，只是借全局者的 Remote Control 把消息送到用户手机上——工作者会话连不上 RC，这是它在这里的唯一作用。所以**不要走「切换触发条件」那套交接协议**：不写交接块，不说切换话术，通知完继续干你的活。

`/allow-once` 只有用户能敲（skill 设了 `disable-model-invocation`）。你不能给自己开窗，也不要去找绕过守卫的其它办法：开窗并不等于授权，它只是让弹窗能弹出来，权限仍然来自用户点的那一下。

## context.md 三块结构

```
## 当前状态           ← 轮换部分每轮由全局者覆盖 + 常驻部分原样带过去(见「撰写权限」)
## 跨 Phase 关键约定  ← 全局者维护。架构、安全、测试、运维约定。用指针,不复制 spec 内容
                        条目分「决定」与「判断」两类,判断类须标最后核实日期
## 本 Phase 历史      ← 工作者和全局者 append。保守规则:只留最近 1 对(latest overseer + latest worker)
```

### 撰写权限

- **「当前状态」** —— 全局者写。唯一例外：工作者可以往 `backlog`、`未验证的前提` 末尾**追加**新条目，不改、不删已有条目，也不碰其余部分。分两部分：
  > 为什么按小节划归属：工作者曾按旧写法「先覆盖当前状态」，把全局者写的轮换内容盖掉了，
  > 历史里「见当前状态→某小节」的指针随之悬空（2026-10-19 一次三轮复审测试里实际发生）。工作者的完成情况写进它自己的交接块。
  - **轮换部分**（每轮由全局者覆盖）：阶段 / 当前任务 / 关键依据文档 / 任务清单
  - **常驻部分**（原样带过去，只按各自的规则增减）：`未验证的前提`、`backlog`、`工作模式`（规则见「工作模式与旋钮表」）。项目要加别的常驻小节时
    加进这份清单，门槛比照 backlog —— 只收不会随轮次自然过期的内容，阶段性信息不算
  - **下文凡说「覆盖当前状态」，都只指轮换部分**（常驻部分怎么处理见各自规则）
> （「未验证的前提」的生命周期规则在 `.workflow/overseer.md`「撰写权限（接）」，工作者平时不读。下面两句是读 `⚠️ 已证伪` 墓碑条目时的判读准则，工作者也要用，留在本文件：）

    - **证伪不等于结论为假。** 常见的是那条推理塌了、结论回到未知。
      按「为假」处理一条其实只回到未知的结论，会把一个从没被正确检验的东西钉死。
  - **未决项必须留在 `context.md`，不管它多旧。** 迁走「过程」是安全的，迁走「未决项」就是丢事 ——
    backlog 一旦随总结进了 `context_history.md`，就只有 grep 才找得到，而没人会 grep 一个自己不记得存在的东西。
    （这条判据来自 qq-bot 2026-07-26：收尾压缩时 backlog 从 context.md 掉进 history，事后核查才捞回。）
  - **准入判据（两条都中才进）：**
    1. 是本轮发现的**真问题或真事实** —— 审查/critic 判定项、过程中发现的非阻塞事实、自知的设计欠债
       （这三类是目前观察到的，不是穷尽枚举）
    2. **不阻塞本轮** —— 阻塞项不许进 backlog，必须本轮解决或按「切换触发条件」切回全局者。
       backlog 最容易被滥用成「不想处理就丢进去」，这一条是门槛
  - **不进 backlog 的四类（最容易搞混）：**
    - **本轮要做的事** → 「任务清单」。注意：两者都是 `- [ ]` 且在同一区块，这是最危险的一处混淆
    - **某条判断没核实** → 「未验证的前提」。backlog 是行动状态（该做没做），
      「未验证的前提」是认知状态（信了没核）
    - **已决定且持续生效的规则** → 「跨 Phase 关键约定」
    - **独立成篇的设计/调研** → `docs/`
  - **条目只能以三种方式离开 backlog，三种都要留痕：**
    标 `[x] 已闭环`；标 `❌ 已否决` 并写明理由；或由全局者在 phase 启动时按优先级
    并入「任务清单」并标 `[x] 已并入任务清单 —— 见任务 N`。
    **第三种同样不许直接删行。** 删掉 = 条目消失且无痕可 grep，正是上面那次丢失的同一形状。
    不许因为「看着旧」「像冗余」就删。只进不出会让它变成坟场，
    所以每次 phase 关闭时全局者要逐条过一遍，能闭环的闭环，不做的明确否决。
    **工作者不得自行从 backlog 认领任务。**「Scope 边界」已规定本轮 scope 严格按任务清单；
    这里再点一次，是因为两个 `- [ ]` 列表同处一个区块，容易看串。
  - **溢出：** backlog 超过约 15 条、或 `context.md` 逼近 300 行时，整体移到 `docs/backlog.md`，
    「当前状态」只留一行指针（写全路径）。**只在装不下时才溢出** —— 移出去之后可见性会下降
    （变成靠指针找），所以这是拿可见性换长度，不是默认做法。
> （「跨 Phase 关键约定」的撰写规则在 `.workflow/overseer.md`「撰写权限（接）」。工作者平时不读；被点名时读这一章。）

- **「本 Phase 历史」** —— 工作者和全局者都 append。新对加入时，旧对挪到 `context_history.md`
  - **条目里不许写指向会被覆盖或迁走内容的指针**：「见当前状态→任务清单」「见顶部」「见上一条」—— 下一轮
    这些内容就不在了，条目进了 `context_history.md` 后指针必然悬空。（条目内部的「同上」「见上文」
    指的是同一条目里的内容，会跟着条目一起走，不算。）要引用就写一句自足的摘要
    （写作契约第 1 条）；指向不随轮换变化的目标可以留指针：`docs/` 下的文件全路径、commit hash、spec 全路径+节名。
    `/as-overseer` 每轮跑 `scripts/ctx-pointers.py` 查前一类写法，命中的在归档前改成摘要
  - **「一对」= 最近一条全局者 + 最近一条工作者，各保留一条。** 连续多轮同角色时
    （如用户直接和全局者对话），只留该角色最新的那条，另一角色的最新条目不动。
    原文「最近 1 对」默认了两个角色交替出现，不覆盖连续同角色的情况 —— 照字面清理
    会把历史区清成单角色。（2026-08-23 music-player 三轮内踩了两次后补，已回流）

### 写作契约（三条）

`context.md` 的主要读者是模型，不是人。这不意味着要写成电报体——**没有「AI 文风」这回事**，缩写和去虚词只会丢信息。真正的差别只有三条，而且都不是风格问题：

**1. 自足。** 判据：**「当前状态」区块，能不能被一个刚启动、什么都没读过的模型直接执行？** 人的交接可以写「继续昨天那个」，因为人有连续记忆；模型没有，而且每一轮都是新的。不能自足就是没写够。同一判据也管「本 Phase 历史」的条目：它们最终要进 `context_history.md`，里面指向「当前状态」的指针到那时已经悬空（见「撰写权限」）。

**2. 标注验证状态。** 模型会自信地基于一条声明行动，不会先问「这条核实过吗」。所以已验证的和推测/待验证的**分开写**，不要混在同一段里。混写的后果不是少一条信息，是让一条未经核实的判断在下一轮以事实的身份被使用。

**3. 绝对化。** 路径写全、日期写绝对值、文件名写全称。不要「上面那个方案」「第三封」「昨天」「刚才改的那个」——人能从上下文还原，模型会**错认且不自知**。

反过来，有一样东西不要为了省 token 删掉：**理由**。没有 why 的规则，模型会把它当成可优化的对象然后「改进」掉；人会犹豫一下，模型不会。所以关键约定要连着当初为什么这么定一起写。

## context.md 写入格式

**时间戳先跑 `date`，不凭感觉。** 下面各格式里的 `[YYYY-MM-DD HH:MM]`，写之前先取一次本机时间：bash `date '+%Y-%m-%d %H:%M'`，PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm'`。模型对「现在几点」没有可靠感知，凭感觉写出来的时间会让条目顺序和事实对不上。

### 工作模式
（常驻部分，原样带过去：模式行、旋钮偏离表、例外记录等。写法见 templates/context.md 同名小节，规则见「工作模式与旋钮表」）

**完成标准尽量交给工具判。** 能用命令判定的（测试、lint、构建、脚本断言），写出命令本身 —— 工作者交接时要贴它的原始输出（见「工作者写入「本 Phase 历史」」的「闸门结果」）。每个闸门标「可重跑」或「不可重跑」：可重跑 = 本仓库内的测试、lint、构建、脚本断言；不可重跑 = 比赛的外部评分提交、依赖外部服务当前状态的检查、需要工作者环境里凭据的、跑很久的、截图类 —— 全局者据此决定能不能自己重跑（见「交接块里另外两个字段」）；没标的按「不可重跑」处理。没有工具能判的质量项（视觉、文案、交互），换成有数据来源的判据，不写「看起来不错」：

- 其余：写一份可观察的断言清单（「按钮在首屏可见」「错误时显示 X 字样」），工作者逐条答是/否并附证据位置

### 工作者写入「本 Phase 历史」（append）

> **动笔之前先提交本轮改动**（完成阶段格式适用；只提交，不 push）：`git add <本轮改的文件，逐个写路径>` + `git commit -m '<沿用项目既有的提交信息风格>' -- <同一路径>`，不用 `git add -A` / `git add .`。
> `context.md` 可以不进这次提交（交接块要写这次提交的 sha，写不进它自己）。「完成情况」开头写 `` 提交：`<sha>`； ``（`git rev-parse --short HEAD` 取）；本轮没有文件改动时写「提交：无（<原因>）」。
> 没提交就交接会被退回：「放行到 `<sha>`」只能指向真实提交，下一轮安全预检的 base-ref 从那里取。

提交之后，写入时**按顺序做两件事**：

**第一步：往「当前状态」的常驻小节追加（只追加，不覆盖）。** 本轮发现但不在本轮处理的事，往 `backlog` 末尾加一条并写明为什么不做；本轮依赖了但没核实的判断，往 `未验证的前提` 末尾加一条并写明核实方式。不改、不删已有条目，**不动轮换部分**（阶段 / 当前任务 / 关键依据文档 / 任务清单）—— 任务完成情况写进第二步的「任务进度」。没有要加的条目就跳过这一步。

> 「本轮发现、不处理」的事不许只写在交接块里：交接块会随轮换进 `context_history.md`，未决项就丢了（见「撰写权限」里「未决项必须留在 `context.md`」）。

**第二步：追加历史记录到「本 Phase 历史」段：**

````
## [YYYY-MM-DD HH:MM] 工作者 — [简短主题]
**完成情况：** 提交：`<sha>`；[阶段结果摘要]（本轮没有文件改动时写「提交：无（<原因>）」）
**任务进度：**
- [x] 任务 1
- [x] 任务 2
- [ ] 任务 3（遗留：[原因]）
**闸门结果：**（完成标准里有工具判定的项时必填，无则「无」）
- [闸门名]（[可重跑/不可重跑]）：`[命令]` —— rc=[退出码]；本轮 [通过/失败]；上一轮 [通过/失败/首次]
  ```
  [命令的原始输出，原样粘贴，不摘要、不改写]
  ```
**spec 修正：**（只限笔误类，见「切换触发条件」第 5 条；无则「无」）
- [文件全路径 + 位置]：改前「…」→ 改后「…」；依据：[对照的真值来源，写全路径]
**关键决策点：**（每项必须显式回答，无则写「无」，不留空）
- 架构/接口变动：[列出，无则写「无」]
- 安全相关：[是否涉及 认证/密钥/用户输入/SQL/文件路径/外部请求，列出涉及项，无则「无」]
- 偏离原计划：[列出与任务清单不符之处，无则「无」]
- 未解决的疑虑：[继续推进但没把握的点，无则「无」]
````

**「闸门结果」的规则**（闸门 = 有工具给出判定的完成标准：测试、lint、构建、脚本断言、截图比对等）：
- **每轮重跑本 phase 已有的全部闸门**，不只跑本轮动过的那几个；逐项和上一个工作者交接块里的结果对比。上一轮通过、本轮失败的，就是回归，在「完成情况」第一句（紧跟开头的「提交：…；」）写明。
- **每条必填 `rc=N`**：命令的退出码，跑完立刻取（bash `echo rc=$?`，PowerShell `$LASTEXITCODE`），不从输出推断。子步骤报错只要没被吞掉，rc 就不会是 0 ——
  所以别让管道吞掉它：先存盘再看尾部，如 `cmd > gate.log 2>&1; echo rc=$?; tail -20 gate.log`，不要 `cmd | tail`。
- **自报必须粘贴原始输出**，不接受「测试全过」这类摘要 —— 摘要正是把回归报成达标的地方。输出超过约 20 行时，原样贴出带判定的尾部（如通过/失败计数那几行），并写明截掉了多少行、完整输出存在哪个文件（全路径）。
- 没有工具判定的质量项（视觉、文案、交互手感）不写进闸门结果，写在「完成情况」里，并按全局者在完成标准里给的判据逐条回答（见「全局者写入「当前状态」」）。

> 为什么不是「让工作者换个读者视角自测」：工作者自查有盲区，换视角还是同一份注意力。能交给工具判的交给工具，并且让全局者看到工具的原话。

> （全局者审查交接块时的核对规则在 `.workflow/overseer.md`「全局者审查交接时」。工作者平时不读，也不要抄进交接块；被点名时读这一章。）
