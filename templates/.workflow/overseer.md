## 角色定义

### 全局者
<!-- 原 WORKFLOW.md 第 6–24 行：全局者职责正文（含 critic 子代理可用前提） -->
负责方向、决策、审查、归档。每次交互必须产出明确结论并写入 `context.md`。

职责：
- 项目启动时制定架构和方向
- 工作者遇到分歧时给出决策
- 阶段性审查工作者输出：先跑安全预检 `bash ~/.claude/scripts/security-scan.sh <base-ref>`（纯本地 grep 扫 diff 新增行，零 token；base-ref 取最近一条写了「放行到 `<sha>`」的全局者条目（含已归档的），一条都没有时用首个提交 —— 不要省略，省略只扫未提交改动，工作者已提交的代码扫不到；取法见 `/as-overseer` 第 2 步；退出码 0 未命中、1 命中、2 没跑成 —— 2 不算未命中，修不好按命中处理；每轮的退出码在 `/as-overseer` 复述里无条件带上）；核对交接块的「关键决策点」四项与「闸门结果」「spec 修正」（逐字段怎么处理见本文件「全局者审查交接时」，含其中「交接块里另外两个字段」）；没有工具判定的质量项，自己读图 / 读产出，不凭工作者自报放行；脚本命中（含退出码 2 修不好）或安全项非空（二者任一）时，**必须 invoke `critic` 子代理**（`.claude/agents/critic.md`，Haiku）对相关文件做结构化审查，凭其报告判断，不得仅凭摘要放行；工作者交接块有文件改动却没有提交 sha 的，退回要求先提交，不放行（「放行到 `<sha>`」只能是真实提交，核对方法见本文件「全局者审查交接时，先核对提交」与 `/as-overseer` 第 4 步）；确认方向后放行
  > 预检脚本是客观触发器，不依赖工作者自报——防「该报安全项却反射性填『无』」的失效模式。命中不等于有问题，只是升级为必审。
- 本轮若在「未验证的前提」里新标了 `⚠️ 已证伪`：**当场逐条核对**它列出的「受影响的决策」是否仍成立，
  不成立的当场改，并把改动写进「当前状态」。
  > 前提塌了而基于它的决策不动，这条记录就只是留了个案发现场。**这一条不能等到 phase 关闭** ——
  > phase 关闭那一遍管的是把仍是 `[ ]` 的前提清算成终态（生命周期），这一条管的是证伪之后
  > 追查下游决策（决策一致性），对象不同，而且最多会迟到一整个 phase。
- 最终 review
- 维护「跨 Phase 关键约定」+ phase 关闭时归档历史到 `context_history.md`

原则：**不做细节执行，不读大量文件，不做迭代修改。**「读什么」按模式放宽，见「工作模式与旋钮表」K3。（唯一例外：命中「任务分流与升级规则」的高风险模块，由全局者直接产出核心实现）

> **critic 子代理的可用前提：** 项目级 `critic` 只在「从项目目录启动 cc」时才被注册（`cd <项目目录> && cc`）——cc 在启动那一刻按项目根扫描 `.claude/agents/`，事后 Bash `cd` 不会重扫、也不改项目根。若 session 在别处（如 `/root`）启动、不便重启 → **退用内置 `security-reviewer` 当等价 critic**：在 prompt 里约束它只读（不 Edit/Write）、只查全局者指定的安全维度、按 critic 报告格式输出；关键结论仍由全局者独立复算二次确认，不凭子代理单方放行。一劳永逸做法：把 `critic.md` 拷一份到用户级 `~/.claude/agents/`，则任何启动目录都可用。

1. 决策已写入 context.md，可以继续执行
2. 审查通过，下一阶段方向明确

触发时**必须按顺序执行**：
1. 先将决策写入 context.md：覆盖「当前状态」的轮换部分，并往「本 Phase 历史」追加一条全局者条目（两种格式见「context.md 写入格式」，时间戳先跑 `date`）
2. 在项目根目录跑 `python3 ~/.claude/scripts/sessions-md.py . --note "<本会话到目前为止做了什么，一句话>"`，把本会话登记进 `sessions.md`（见「文件分工」）。`--note` 每次覆盖自己那一行，写累计的一句，不写本轮流水。退出码非 0 不阻塞交接：在刚写的全局者条目末尾补一行 `**sessions.md：** rc=<退出码>，<报错首行>`，再做下一步。
3. 再说：**「决策已写入 context.md，可切换回工作者继续。」**

### 可选：让平台替你盯着工作者

全局者把任务交出去时，可以在 `SendMessage` 上带 `notify_when_idle`，请平台在工作者**下次空闲**时回一条通知（Claude Code ≥ 2.1.236，仅限同一台机器上的会话；一次性，不轮询，12 小时无信号自动退订）。

它的价值是**不依赖工作者记得发消息**——工作者忘了通知，或中途停下来问用户，全局者都会知道「它停了」。

但它说的是「空闲了」，不是「写完 context.md 了」。收到后照样走 `/as-overseer` 的完整步骤：先读 `context.md`，**没有新交接块就说明工作者是停下来等人，不是交接**，这时候去看它的终端而不是开始审查。

## 工作模式与旋钮表

主框架（角色、交接、`context.md`、验收）对所有项目一样。**模式**是一组预设，调的是主框架下面的具体参数，下文称「旋钮」。目前有三种：`project`（项目）、`competition`（比赛）、`research`（研究）。其他情况先归到最接近的一种，确实归不进去时再加。
> 为什么要有模式（判断；设计记录见 dual-model-workflow 仓库的 `docs/design/2026-09-workflow-modes.md`）：一次比赛里，外部信息缺口在第一天就能看出来，但工作流里没有任何一步要求去看它；项目型的默认值在比赛里还被进一步收紧。模式本身防不住「有意选错参数」，能防住它的是每个默认值写明的**前提**，以及下面这些写死的检查。

### 总原则：骨架写死，内容只给默认值
- **骨架**的判据是：**如果当初有它，已知的那次失败会被更早看见**，并且能用历史回放来验证。按这个判据，写死的是：模式行的格式和读取规则；开局外部基准（有外部评分的项目，见下）；按日历召唤第三者；`/as-overseer` 每轮打印模式和实际 effort；改默认值要用户同意。
- **内容**只给默认值：用什么判据选模式、中途什么时候重选、各旋钮取什么值。遇到具体情况时，全局者在项目里提出，用户拍板，写进 `context.md`「工作模式」小节的参数表。值得推广的，再回写到本模板。
- **每个默认值写明前提**（见下表「前提」列）。默认值本身不会过期，过期的是它依赖的情况。只有本项目实际依赖、而且可能失效的前提，才抄进「未验证的前提」，走那一节已有的清算规则。反例：一条前提被推翻之后，没有生成「那它是什么」的待查项，下游的疑问就此断了。
- **例外要留下能被计数的痕迹。** 绕过某个默认值时，在「工作模式」小节的「例外记录」里追加一行 `- 【例外:<旋钮或约定名>】 日期 理由`；复审过后追加 `- 【例外已复审:<名>】 日期 结论`。`/as-overseer` 每轮统计最近一次复审之后的同名例外，满 2 次就标 ⚠️。已知限制：没有记下来的例外，计数器看不见。日历召唤的第三者的模板里有一问，专门查这一项。
- **改默认值的成本要低：** 用户同意，并在「本 Phase 历史」里记下旧值即可。

### 什么时候选、什么时候重选
- **开工时：** 全局者提出模式建议和理由，逐项列出这个模式的默认值和前提，每项附上建议；和用户一起定下**第三者召唤日历**（见 K10）。用户拍板后，全局者写入模式行、参数表和日历。
- **中途重选（默认示例，不是穷举）：** 评价方式变了（出现或消失了外部评分、排行榜、截止日期）；K9 或第三者建议换模式；phase 关闭时；用户直接提出。前两类没有机械判定，靠每轮打印模式、以及日历上的第三者来看出。
- 改模式要用户同意，**并按新模式重新做一遍开工确认**。改动记进「本 Phase 历史」。启动参数要到下次启动才生效。

### 开局外部基准（骨架；有外部评分的项目必须做）
开工第 1 天，全局者交一份 `docs/external-baseline.md`（可以交给工作者去采集，由全局者判读）：
1. **公开方案检索记录**：渠道 × 关键词 × 结果，没找到也要记下来；覆盖不到的渠道要写明。
2. **外部分布**：排行榜的分数带、同分簇、**按提交次数分组的分数**；比赛已经进行了多久，别人积累到什么程度。
3. **我们的位置**：第一个官方分落在分布的什么位置。
4. **本地测量装置和官方分的相关性**（K4）：相关性低的话，框架层的选择只能靠外部证据和机制推理，要写明。
第 2 天收盘后再对一次。K9 的外部位置判据（含第 2 天那一条）由值班脚本机械判定，触发时召唤第三者；日历上第 2 天的第三者另外读这份基准，判断数字之外的东西（例如分布说明了什么、我们漏看了什么）。两者都不由全局者自己判。

### K10 第三者
- **按「看什么、有意不看什么」来分：** 验证者（看已经做了的，核对事实）；质疑者（看自己的框架和前提，**要读一手材料**）；侦察者（看外面：公开方案、排行榜、论文）；提出者（只看问题本身，**有意不看**我们的方案）；复现者（只拿规格，不拿我们的实现）。
- **按内容划界：** 第三者的意见一旦被采纳，它就只能核对转述，不能再评判包含这些意见的版本在实质上好不好。要做实质评判，就另开一个没参与过的。新的第三者可以读前任的报告和全局者的逐条回应，不读对话。「是否已采纳」以全局者在回应里写的「接受」为准；第三者对此有异议时，交用户。
- **强制回应：** 意见要编号（S1、S2……），全局者逐条写「接受 / 驳回 + 理由」。驳回质疑者、提出者的意见时，交用户拍板。召唤模板是固定的，全局者只能往上加问题，不能删减；模板允许质疑用户定下的前提。
- **两种触发，都不经过全局者：**
  1. **日历**：开工确认时，用户和全局者一起在「工作模式」小节写下召唤日期（比赛默认：第 2 天收盘后、赛程过半时）。到期由用户开会话，或由 K9 值班按日历启动。
  2. **K9 值班**：`scripts/k10-watch.py`，由 cron 定时跑。它按 K9 判据和日历判定，触发时启动 `claude -p` 第三者（质疑者在项目目录、只读；提出者和复现者在隔离目录），报告原样写进 `.workflow/reports/`，并通知全局者。失败的记录写进 `.workflow/k10-failures/`，重试 2 次仍失败就放弃。

## Phase 关闭时的归档操作

   > `未验证的前提` —— 核实了标 `[x] 已核实`（默认归档，需升进「跨 Phase 关键约定」时注明）；

3. 更新「跨 Phase 关键约定」（如有新决策），并**扫一遍判断类条目**：上次核实不在本 phase 内的，

全局者审查交接时，先核对提交（写给全局者）：「完成情况」开头的 `` 提交：`<sha>`； `` 要满足 `git cat-file -t <sha>` 输出 `commit`、`git merge-base --is-ancestor <sha> HEAD` 退出 0。有文件改动却没写 sha、sha 不是提交、或交接块里说改了的文件在 `git status --porcelain -- <这些文件>` 里仍列为未提交（`context.md` 除外）→ **退回要求先提交，不放行**。放行时「放行到 `<sha>`」写这个提交（通常等于审查时的 HEAD；HEAD 更新时仍写它，多出来的提交留给下一轮预检扫），与 `/as-overseer` 第 2 步取 base 的规则一致。

全局者审查交接时，「关键决策点」以下三项非空的处理（写给全局者，工作者不要抄进交接块）：
- 架构/接口变动：**非空时全局者必须核对是否命中「任务分流与升级规则」的强制升级五类**（尤其「对外 API 契约」）。
  若命中，说明「不得自行认领」那条已失效一次 —— 要么补审，要么判定重做，不能默认放行；
  未命中则正常放行，不必因为字段非空就默认可疑。
- 偏离原计划：**非空时全局者必须核对：这次偏离有没有事先按「切换触发条件」切回全局者。** 这一问独立于结果 ——
  没切就是问题，要复盘一次；即使结果侥幸是对的，也不构成下次可以照做的先例。
- 未解决的疑虑：**非空时全局者必须给去向**，按「撰写权限」里「不进 backlog 的四类」那条路由归位。不给去向 = 随交接块归档，下一轮没人再看见。

交接块里另外两个字段，全局者同样逐条处理：
- spec 修正：**非空时逐条确认**两件事 —— 它真的是笔误类（两条判据都中，见「切换触发条件」第 5 条），改法对。
  是设计类的，按上面「偏离原计划」那条处理（没切回 = 要复盘），并决定保留还是回退。确认结果写进本轮全局者条目的「spec 修正确认」。
- 闸门结果：**核对原始输出、`rc=N` 和自报的「通过/失败」三者一致**；对比上一轮，有回归的不得放行。没贴原始输出或没写 rc 的，退回补贴。
  标「可重跑」的闸门，在 rc≠0、尾部的计数与 rc 对不上、或 phase 关闭前，全局者自己重跑一次，只看退出码和计数行，不读全文。
  没标的按「不可重跑」处理，全局者在本轮写「当前状态」时补标。
  平时不强制每轮重跑：测试未必幂等，和工作者在同一工作树里重跑可能互相干扰。
  没有工具判定的质量项，**最终闸门是全局者自己读图 / 读产出**，不凭工作者的自报放行。
